# Eefi Browser: architecture and staged roadmap

## Architecture

- **Rendering and browser engine:** Tauri 2 with WebView2 on Windows. The browser chrome is a small Svelte/TypeScript application; each page tab is a separate native child webview. No custom HTML or JavaScript engine is used.
- **Native core:** Rust modules own tab lifecycle, URL classification, navigation policy, and later persistence and privacy services. The webview adapter is isolated behind the tab/navigation modules so a future CEF adapter can replace it without coupling storage and browser UI to Tauri.
- **Stage 2 storage:** SQLite is opened on blocking workers through `StorageService`; legacy schema migrations are serialized, and repositories cover bookmarks/folders, history, downloads, settings, and saved tabs. The current schema marker remains at version 6 for compatibility with older browser builds. Future changes must be additive and backward-compatible without advancing `PRAGMA user_version`. The development bundle identifier isolates its profile from other installed browser profiles.
- **UI/native boundary:** The browser chrome calls a narrow, validated Tauri command API. Commands resolve per-window state from the invoking `Webview`'s host window, which also works when the chrome is a child webview rather than a `WebviewWindow`. Native page events update tab titles and addresses. External page content is kept in separate webviews; its app-command permissions are limited to page-scoped DevTools, print-dialog, and find-bar actions.
- **Persistence and async work:** Stage 2 introduces SQLite (`rusqlite`) behind storage repositories and moves blocking database, downloads, and parsing work off the UI thread. Native child-webview creation, waking sleeping tabs, and WebView2 interception setup run on a blocking worker and complete before tab activation. Later services use asynchronous task boundaries and explicit shutdown handling.
- **Security:** Browser chrome has a restrictive CSP. Tauri app-command ACLs grant its trusted UI the browser command set; remote HTTP(S) page webviews receive only page-scoped DevTools, print-dialog, and find-bar actions, with native handlers validating that page calls can only target the calling page. Find results and PDF exports are resolved only for browser-owned tab IDs in that host window. The remote capability is scoped to the normal/private host windows and URL schemes, since Tauri matches capability window labels against the host window rather than a child webview label. All browser chrome windows load the bundled Tauri app origin; remote sites are not granted the chrome command set. Navigation accepts only HTTP(S) destinations or encoded search queries. Stage 3 adds native WebView2 interception, private-window profile isolation, site permissions, privacy preferences, and bounded user-managed filter lists/rules. Scriptlet resources are bundled from a pinned legacy uBlock format; cosmetic rules are also applied in open shadow roots. The development-only live-verification fixture passes its documented local WebView2 checks; this does not establish universal filter compatibility.
- **Performance:** The startup path creates only the shell and initial webview. Rust release builds use LTO, a single codegen unit, abort-on-panic, and stripped symbols. Inactive page webviews are discarded after a configurable idle timeout and reloaded from their current URL when selected; page-local state and back/forward history are not retained across sleep.
- **Home and new tabs:** Blank tabs and the Home button show a local browser-chrome page with search and bookmarks-bar shortcuts. The corresponding page webview is hidden while this page is shown; searches and shortcut selections navigate through the normal browser URL handling.
- **Recently closed tabs:** The last ten closed tabs are kept in memory per window and can be reopened from the Browser menu or with `Ctrl+Shift+T`. URLs, titles, and existing tab groups are restored; this list is not persisted across browser restarts, and moving a tab to another window does not count as closing it.
- **Single-page navigation:** WebView2's native history-change event reads the current source URL and updates tab state, the address bar, and recently closed-tab snapshots. This captures route and query changes without relying on page-script IPC.

## Roadmap

1. **Shell (this stage):** Browser chrome, native tabs, address/search parsing, back/forward/reload/stop/home, keyboard shortcuts, and a working Windows WebView2 development build.
2. **Data features:** SQLite storage, bookmarks, history, downloads, session restore, import/export, and their repository tests.
3. **Privacy and ad blocking:** Native request interception, filter engine, site controls, privacy headers, opt-in HTTPS-only upgrades, data clearing, per-site permissions, private windows, cookie-request controls, clear-on-exit, an asynchronously updated malware domain list, and bounded custom filter lists/user rules are implemented. Cosmetic injection supports matched CSS, generic class/ID rules, bundled legacy uBlock scriptlets, open shadow roots, and a bounded subset of procedural text/action rules. Current uBlock ES-module/trusted scriptlet resources and closed shadow roots are not supported. The development-only WebView2 fixture passes its documented local checks; this does not establish universal filter compatibility or remove runtime-specific coverage limits.
4. **Passwords and autofill:** An initial Windows DPAPI-protected password vault is implemented. Password save prompts, automatic page fill, address/payment profiles, master password, and import/export remain future work.
5. **Extensions, developer tools, and polish:** A local home/new-tab page provides search and bookmarks-bar shortcuts. Other remaining work includes full DevTools integration, accessibility and appearance settings, and remaining browser features. The initial DevTools slice adds the browser-menu action and an F12 page shortcut backed by a page-label-validated command; the user confirmed opening and closing behavior works. The user-script manager is implemented and its page injection was live-tested. Initial named/color tab groups are implemented with per-window membership and normal-session persistence. Normal windows can be opened independently, and a tab can be moved to a new window from its context menu. Secondary-window tabs/groups are isolated from other windows but are not restored across app restarts; only the main window uses the saved session.

Each stage is a separately verifiable increment. Features listed in later stages are not claimed as present before their implementation.

## Stage 1: run and verify

- Install frontend dependencies with `npm install`.
- Start the desktop browser with `npm run tauri -- dev` (Windows requires WebView2 and the Rust MSVC toolchain).
- Type-check and build the UI with `npm run check` and `npm run build`.
- Run the native URL parser tests with `cargo test --manifest-path src-tauri\Cargo.toml`.

Stage 1 includes working native tabs, drag reordering, omnibox URL/search routing, navigation controls, loading/stop state, and keyboard shortcuts.

## Stage 2: delivered features and limits

- SQLite-backed bookmarks and folders, bookmarks bar, search, edit/delete, and Netscape HTML import/export. HTML import/export currently treats bookmarks as a flat list; it does not preserve folder nesting.
- Searchable history with site deletion, time-range clearing, and a clear-data dialog. The dialog can remove history, cookies/site data, and disk cache; history supports a time range, while cookies/cache currently clear for all time.
- Download records from WebView2 start/completion events, byte progress, pause/resume/cancel controls, a configurable destination folder, optional Windows Save As prompts, open/reveal actions, and warnings for executable file extensions. Progress and operation handles are session-only; SQLite schema version 6 remains unchanged. Active rows are retained when clearing completed records.
- Session tabs and active-tab state are saved off the UI thread and restored on startup. History, bookmarks, downloads, and session data are currently stored locally without encryption.

Run the app with `npm run tauri -- dev`. Validate the UI with `npm run check` and `npm run build`, then run Rust URL and storage tests with `cargo test --manifest-path src-tauri\Cargo.toml`.

The Rust integration suite lives in `src-tauri/tests/backend_workflows.rs`. It uses temporary on-disk profiles and verifies workflows across URL classification, SQLite-backed bookmarks/history, download completion and restart recovery, session groups/revision ordering, and legacy-profile migration. Run it alone with `cargo test --manifest-path src-tauri\Cargo.toml --test backend_workflows`; the full Cargo test command runs the integration suite together with the inline unit tests. These tests exercise Rust services and persistence, not the desktop UI or WebView2 runtime.

## Stage 3: native ad blocking and initial privacy controls

- Every page-tab WebView2 instance gets a native `WebResourceRequested` handler before it navigates to its requested URL. On runtimes exposing `ICoreWebView2_22`, the filter is registered for every resource context and request source kind; older runtimes use WebView2's earlier context filter, whose worker/source-kind coverage is narrower.
- The `adblock` Rust engine starts with a small built-in ruleset, asynchronously loads cached EasyList/EasyPrivacy and URLHaus malware-domain rules, refreshes stale lists on a 24-hour schedule, and persists both raw lists and a serialized engine cache. Filter download, parsing, and database operations run off the UI thread.
- The toolbar exposes global blocking and exact-host allowlisting controls with a blocked-request counter. Those preferences are persisted in SQLite; schema version 2 adds the site permission table.
- Page-created windows are denied by default by the Tauri/WebView2 new-window handler.
- Outgoing web requests attempt to include `DNT: 1` and `Sec-GPC: 1`; failures are logged and do not prevent navigation.
- HTTPS-only mode is an opt-in privacy setting persisted in SQLite. When enabled, the native request handler rewrites intercepted `http://` requests to `https://` before sending them; it does not silently retry over HTTP when HTTPS is unavailable.
- Private windows use Tauri/WebView2 incognito mode in both the chrome and page webviews and maintain separate, window-scoped tab state. They do not restore or persist session tabs, history, or download metadata. WebView2 requires runtime 101.0.1210.39 or newer for incognito mode; the private-window command checks this requirement and returns an explicit error on older runtimes.
- The optional third-party cookie control strips the `Cookie` request header from cross-site requests using schemeful registrable-domain checks. WebView2 can still store cookies received in cross-site responses; this is not a full third-party cookie storage block.
- Privacy settings support up to eight HTTPS custom filter-list URLs and 64 KiB of custom Adblock Plus rules. Downloaded lists are limited to 8 MiB each and 16 MiB total cache; settings and cached sources survive restarts. Applying changes rebuilds the engine asynchronously, and custom-list refresh failures are returned to the settings UI rather than silently discarded.
- Clear browsing data uses WebView2 profile APIs to remove cookies and/or disk cache in addition to the browser's SQLite history. The optional clear-on-exit setting defers app exit until cookies and disk cache are cleared; it does not clear history or other site storage automatically.
- Camera, microphone, location, notifications, and clipboard-read requests are denied unless the exact requesting origin has an explicit grant in the Privacy settings panel. The permission table is schema version 4; unrecognized permission kinds retain WebView2's default behavior.
- WebView2 document-start hooks inject matched cosmetic CSS and scriptlets into the main document and navigated frames. Script registration completes asynchronously and never blocks a navigation callback. Generic class/ID rules are matched natively from bounded DOM token batches; messages are restricted to the active frame URL and capped per navigation. Procedural cosmetics support a bounded set of CSS selectors with case-sensitive literal `:has-text()` checks and remove/style/remove-attribute/remove-class actions; regex text matching and other procedural operators are skipped. Per-page rule limits and animation-frame work batches bound work on dynamic pages. An early bootstrap observes dynamically created **open** shadow roots and installs the same cosmetic processors there; closed roots are inaccessible. The bundled scriptlet resources use uBlock's pinned legacy text-template format, so current ES-module/trusted resources in the live uBlock filter list may not resolve. Script registrations are removed as frames navigate or are destroyed; global disable and exact-host allowlisting suppress cosmetics. WebView2's resource callback does not identify a document request's frame, so top-level `document` versus `subdocument` network-filter classification remains approximate.
- The toolbar menu opens a command menu for new tabs, private windows, library pages, and privacy settings rather than navigating directly to History. URLHaus malware-domain matches are blocked at top-level navigation and replaced with a browser warning page. Unit tests cover WebView2 resource-context mapping, network filter exceptions, allowlisting, and cosmetic policy. The live WebView2 fixture passes checks for scriptlets and cosmetics in the top page and same-origin frame, fetch/XHR/image/document/frame/worker request blocking, and popup behavior. These checks cover the exercised local paths only; document versus subdocument classification remains approximate, and WebView2 runtime versions can differ.

Run with `npm run tauri -- dev`. Validate native behavior and schema migrations with `cargo test --manifest-path src-tauri\Cargo.toml`; check and build the frontend with `npm run check` and `npm run build`. Toggle HTTPS-only mode from the toolbar's Privacy settings button. The first run uses built-in rules while cached filter lists download in the background.

For local WebView2 verification, run `npm run tauri -- dev --features live-verification`; Tauri's `beforeDevCommand` starts Vite before launching the app. Navigate to `http://localhost:1420/__stage3__/fixture.html`. The fixture probes scriptlet and shadow cosmetics in the top page and a same-origin frame, plus worker, fetch, XHR, image, document, and popup behavior. Its test-only filters are scoped to `localhost` and excluded from normal builds. Blocked requests are replaced with empty HTTP 204 responses, so the fetch/XHR checks expect that status (not a rejected promise); the toolbar's blocked counter should also increase. The current live run passed all 21 fixture-reported checks; confirm popup blocking by checking that no new browser window opens. A fixture pass is not proof of all real-world frame or worker coverage.

## Stage 4: initial OS-protected password vault

- Password credentials can be entered, generated, listed, explicitly revealed, and deleted from the browser chrome. Generation uses Web Crypto and rejection sampling.
- On Windows, credential JSON is protected with the current user's DPAPI before it is written to SQLite. Origin metadata remains visible for lookup; usernames and passwords remain encrypted at rest. The vault is bound to the Windows user account and has no master-password or cross-device export flow.
- The vault does not inspect page forms, prompt after login, or autofill websites. Address and payment profiles are not implemented.

## Stage 5: initial DevTools, user scripts, and tab groups

- The browser menu and F12 shortcut toggle WebView2 DevTools for the active page. The shortcut is injected into page frames and invokes a command that can toggle only its calling page webview. The user confirmed opening and closing behavior.
- Ctrl+F opens a browser find bar and uses WebView2's native find API to search and highlight matches across the page, with previous/next navigation and match counts. It requires a WebView2 Runtime exposing the find interfaces.
- Ctrl+P opens the WebView2 print dialog from the browser chrome or an individual page. **Save as PDF** uses WebView2's `PrintToPdf` API and the native Save dialog; sleeping tabs must be woken first. Both operations require a WebView2 Runtime exposing the relevant print interfaces.
- Tauri app-command permissions are generated for the registered browser commands. The browser-chrome capability grants the UI command set; the remote-page capability matches the host window and HTTP(S) URL, and grants only the page-scoped DevTools, print-dialog, and find-bar requests.
- DevTools opens in WebView2's separate inspector window rather than a docked browser panel.
- User scripts can be created, edited, enabled/disabled, and deleted from the browser menu. Scripts are stored in SQLite; new scripts default to disabled and are limited to 64 scripts, 64 KiB of source each, and a specific HTTP(S) hostname pattern (exact or `*.` subdomains) with a path glob. There is no global-host wildcard, remote script loader, import/export, or WebExtensions API. The user live-tested page injection successfully.
- Enabled scripts execute in the matching top-level page after load in normal windows. They are not isolated from page JavaScript and can access or modify page content, so only trusted code should be enabled. Scripts do not run in private windows or subframes; saved changes apply after reloading the page. These limits are intentional for this initial slice.
- Tab groups can be created for the active tab, renamed, recolored from a fixed palette, assigned additional tabs, and deleted from the browser menu's Tab groups manager. Each tab belongs to at most one group. The tab strip remains flat and drag-reorderable; collapsing groups is not implemented.
- Normal-window groups and memberships are saved with the restored session. Private-window groups are isolated to that window and are not persisted.
- The Browser menu can open a separate normal window. Right-clicking a tab offers **Move tab to new window**; the tab's URL, title, and group are carried over, and moving the last tab leaves a blank tab in the source window. Each window has its own native tab state. Only the main window is included in session restore; additional normal windows are not yet restored.
- Tab sleeping discards inactive page webviews after a persisted timeout (15 minutes by default; 1, 5, 15, 30, or 60 minutes, or never). Selecting a sleeping tab reloads its current URL and restores normal browser controls, but does not preserve that page's in-memory state or back/forward history.
